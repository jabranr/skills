# `jabraf-skills-index`

This one skill covers the whole library, so an environment only needs it
installed. It lists every skill, says when to use each one, and gives a
`target` URL to load it from.

## Steps

1. **Pick.** Match the task to the catalog below. When two skills look like a
   fit, check **Overlaps**. A task can need several skills, one per concern
   (for example spec, then plan, then TDD). Done when each concern in the task
   has a skill, or you have checked the catalog and nothing fits (then go on
   without a skill).
2. **Load** each picked skill, using the first route that works:
   1. The skill is already available in this environment (it is in your skill
      list, under its own name or, for a skill tagged with a plugin, as
      `<plugin>:<name>`): invoke it the normal way.
   2. Run `npx -y skills@1.5.12 use <target>` with the skill's target. The
      output is the skill's `SKILL.md`, followed by a temporary directory that
      holds its supporting files. Follow that output as if the skill had been
      invoked, and read any relative path it mentions from that directory. Load
      each skill once per session.
   3. If `npx` or git is not available, fetch
      `https://raw.githubusercontent.com/<owner>/<repo>/<branch>/<path>/SKILL.md`
      (the same parts as the target URL) and fetch each relative file it
      mentions from the same base.

   Done when the skill's instructions are in context. If no route works, tell
   the user which skill could not be loaded and why.

3. **Chain.** When a loaded skill tells you to use another skill (for example
   `jabraf-dev-setup` uses the granular `jabraf-*` skills), find that skill in
   this index and load it the same way.

The targets are the library the user chose. Whatever a route loads from them
counts as an installed skill.

## Overlaps

- **Tests:** `test-driven-development` is the default for any logic change or
  bug fix. Use `tdd` when the user asks for test-first work, red-green-refactor
  or integration tests by name.
- **Review:** `code-review-and-quality` reviews one diff or PR.
  `code-review` reviews everything since a fixed point against the repo's
  standards and the spec it came from.
- **Shaping:** `idea-refine` is for a vague idea that needs options.
  `interview-me` finds the user's real intent when the ask is underspecified.
  `grilling` stress-tests a plan the user already has, and `grill-with-docs`
  does the same while recording ADRs and a glossary.
- **Bugs:** `debugging-and-error-recovery` is the default when something
  breaks. Use `diagnosing-bugs` for a hard bug or performance regression that
  has resisted a first pass.
- **Spec to code:** `spec-driven-development` writes a spec. `to-spec` turns
  the conversation into a spec on the issue tracker. `implement-spec` builds
  from what `to-spec` produced, and `implement` builds from any spec or
  tickets. Whichever builds, `incremental-implementation` sets the size of each
  slice.
- **Browser:** `playwright-cli` is the default for driving a page (open,
  click, fill, snapshot). Use `browser-testing-with-devtools` for DevTools
  work such as network, console and performance profiling. Prefer both over
  a Playwright MCP server, and prefer `gh` over a GitHub MCP server.
- **Architecture:** `codebase-design` designs a single module.
  `improve-codebase-architecture` scans the whole codebase for improvements.
- **UI:** `hallmark` is for new sites and pages. `frontend-ui-engineering` is
  for components and app UI in existing code. `stageshow` is for faux product
  UI and demo animations. `frontend-design` is general visual-design guidance
  for any UI, and `unslop` reworks UI that already looks generic.
- **Remotion:** start with `remotion-best-practices`. When it points to a
  sibling such as `./remotion-create/`, load that skill from this index.
- **Motion:** `animate` builds an animation. `review-animations` critiques
  existing motion code. `improve-animations` audits the whole codebase.
- **CI:** `ci-cd-and-automation` covers pipelines in general. The
  `jabraf-workflows-*` skills wire up `jabranr/workflows`, so use them first in
  Jabran's repos.
- **Pre-commit hooks:** use `jabraf-lint-staged` in projects on `@jabraf/dev`,
  and `setup-pre-commit` everywhere else.
- **Baseline:** `jabraf-ground-rules` applies to every task in Jabran's repos.
  Load it together with the task's own skill.
